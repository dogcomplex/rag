Data Pipeline and Transformation Suite
GraphRAG's data pipeline and transformation suite converts raw, unstructured text into a structured knowledge graph. This process involves several stages, starting with initial data ingestion and preparation. GraphRAG loads diverse data types, including CSV, JSON, and plain text, into a standardized format, usually Pandas DataFrames. It handles file discovery, parses content, injects metadata, and standardizes columns, ensuring data is uniformly prepared for subsequent processing. Unique identifiers are generated for consistency across the system.

Following ingestion, the pipeline processes text by segmenting it into manageable TextUnit objects using various chunking strategies, such as token-based or sentence-based methods. This segmentation is crucial for managing the context fed to Large Language Models (LLMs) and for the subsequent construction of the knowledge graph. A preliminary graph is then built by extracting noun phrases from these text units as nodes and identifying their co-occurrence as edges.

The next stage involves the extraction of structured entities and relationships from the text units, often leveraging LLMs. This process identifies key concepts (entities) and the connections between them (relationships), consolidating them into DataFrames. GraphRAG also supports the extraction of structured claims, referred to as covariates, which are additional metadata associated with entities.

Once the initial graph is constructed, it undergoes enrichment and analysis. This includes generating numerical vector representations for both text content and graph nodes through embedding operations. Text embedding creates vector representations of text units and entity descriptions, while graph embedding uses algorithms like Node2Vec to capture the structural information of the graph. Clustering algorithms, such as the Leiden algorithm, are applied to identify communities within the graph, grouping related entities and relationships. Graph metrics like node degrees are computed, and the graph can be pruned based on configurable criteria to manage complexity. Layout algorithms are also applied to provide spatial coordinates for graph visualization.

Finally, the system summarizes various graph components. This involves generating concise descriptions for entities and relationships and orchestrating the creation of structured community reports. These reports leverage LLMs to produce summaries of identified communities, managing hierarchical contexts and token limits to ensure coherent and relevant outputs. The entire indexing pipeline is designed with robust incremental indexing capabilities, allowing for efficient updates, merging, and conflict resolution when new data is introduced, thus maintaining data consistency over time. More details on the overarching architecture and its key components can be found in Overall Architecture and Key Components.

Indexing Engine
The GraphRAG indexing engine orchestrates the transformation of unstructured text into a structured knowledge graph, serving as the core component for building and maintaining these knowledge structures. This engine manages the entire lifecycle, from initial data ingestion to advanced graph analysis and the generation of structured reports, all within a configurable and often asynchronous framework.

The process begins with Data Loading and Preparation, where various data types—such as CSV, JSON, and raw text—are ingested from storage and standardized into Pandas DataFrames. This step ensures consistent input for downstream processing, handling file discovery, content parsing, and metadata injection.

Following data loading, the system moves into Text Processing and Graph Construction. Here, raw text is segmented into manageable units, and a preliminary graph is built by extracting noun phrases and identifying their co-occurrence. This initial graph provides a foundational structure for more detailed knowledge extraction.

The extracted noun graph is then refined through Entity and Relationship Extraction. Large language models are leveraged to identify structured entities and relationships from the text units, along with claims (covariates). These extracted components are consolidated into DataFrames, forming the basis of the knowledge graph.

The graph undergoes further Graph Enrichment and Analysis, which includes generating numerical vector representations for both text content and graph nodes, a process known as Text and Graph Embedding. Clustering algorithms are applied to identify communities within the graph, and layout algorithms assign spatial coordinates for potential visualization. Graph metrics, such as node degrees, are also calculated, and the graph can be pruned based on defined criteria.

Finally, the system performs Graph Component Summarization. This involves generating concise descriptions for entities and relationships, and orchestrating the creation of structured community reports using language models. These reports synthesize the information contained within the graph's communities, managing hierarchical contexts and adhering to token limits.

A key capability of the indexing engine is its Incremental Indexing Capabilities. This functionality allows for efficient updates to existing knowledge graphs by identifying changes in input data, merging new information with existing structures, resolving conflicts in entities, communities, and relationships, and ensuring unique identifier assignments. This ensures that the knowledge graph remains current and consistent over time without requiring a full rebuild.

A critical aspect of data preparation is standardization, managed by utilities within graphrag/index/input/util.py. The process_data_columns function ensures that every record, regardless of its original format, contains id, text, and title columns. If an id is missing, a stable SHA-512 hash is generated using gen_sha512_hash (from graphrag/index/utils/hashing.py) to provide a consistent identifier. Text and title columns are mapped according to configuration or assigned default values. This standardization is vital for ensuring that all downstream indexing operations, such as graph construction and entity extraction, receive data in a predictable and usable format.

The overall design emphasizes asynchronous operations to enhance performance, especially when dealing with numerous or large files. Configuration objects centralize parameters for file patterns, encoding, and column mappings, allowing for flexible adaptation to various input sources without altering core logic. The robust file loading utility, load_files (from graphrag/index/input/util.py), also manages error handling, logging warnings for problematic files, and skipping them to prevent a single corrupted file from halting the entire data ingestion pipeline.

Text Processing and Graph Construction
GraphRAG begins text processing by transforming raw input into TextChunk objects. This initial segmentation uses strategies that can be configured for token-based or sentence-based chunking. For instance, token-based chunking, managed by functions like run_tokens in /microsoft/graphrag/graphrag/index/operations/chunk_text/strategies.py, utilizes tiktoken to adhere to specified token limits and overlaps, ensuring that text segments are appropriately sized for subsequent language model processing. Sentence-based chunking, on the other hand, leverages NLTK's sentence tokenization capabilities, which are initialized as needed by bootstrap in /microsoft/graphrag/graphrag/index/operations/chunk_text/bootstrap.py to ensure efficient resource management. Each TextChunk object, defined in /microsoft/graphrag/graphrag/index/operations/chunk_text/typing.py, contains the text content, its original document indices, and its token count, facilitating traceability and downstream analysis.

Following text chunking, GraphRAG constructs a preliminary graph by identifying and extracting noun phrases. This process, orchestrated by build_noun_graph in /microsoft/graphrag/graphrag/index/operations/build_noun_graph/build_noun_graph.py, represents noun phrases as nodes and their co-occurrence within the same text units as edges. Various noun phrase extraction methods are supported and can be dynamically selected based on configuration, as detailed in Configuration Models and Validation. These methods range from Context-Free Grammar (CFG) based extraction, which iteratively merges tokens based on grammatical rules as implemented in /microsoft/graphrag/graphrag/index/operations/build_noun_graph/np_extractors/cfg_extractor.py, to more accurate syntactic parsing methods using SpaCy's dependency analysis, found in /microsoft/graphrag/graphrag/index/operations/build_noun_graph/np_extractors/syntactic_parsing_extractor.py. A factory pattern, exemplified by create_noun_phrase_extractor in /microsoft/graphrag/graphrag/index/operations/build_noun_graph/np_extractors/factory.py, ensures that the appropriate extractor is instantiated based on the desired level of linguistic sophistication and performance. Extracted noun phrases undergo filtering using heuristics such as token length, part-of-speech tags, and compound word presence, with utilities like is_valid_entity in /microsoft/graphrag/graphrag/index/operations/build_noun_graph/np_extractors/np_validator.py to refine the quality of the resulting graph nodes. The edges representing co-occurrence are assigned weights, which can be normalized using techniques like Pointwise Mutual Information (PMI) for a more robust measure of association. This initial graph provides a structured foundation for further enrichment and analysis within the GraphRAG framework.

Text Chunking Strategies
GraphRAG employs various strategies to segment raw text into smaller, manageable TextChunk objects, which are crucial for subsequent processing steps in the indexing pipeline. This modular approach allows for flexibility in how text is prepared for knowledge graph construction and large language model interactions. The core logic for text chunking is encapsulated within the graphrag/index/operations/chunk_text directory.

One primary method for text segmentation is token-based chunking. This strategy leverages a TokenTextSplitter (found in graphrag/index/text_splitting/text_splitting.py) to divide text based on token counts rather than character counts. The TokenTextSplitter can be configured with specific tokens_per_chunk and chunk_overlap settings, ensuring that chunks adhere to desired token limits and maintain continuity between them. This is particularly important for consistency with large language models that process text in terms of tokens. The actual splitting process for multiple texts concatenates token IDs while retaining original document indices, ensuring traceability of chunks back to their source documents.

Another significant approach is sentence-based chunking. This method uses natural language processing (NLP) capabilities to identify sentence boundaries and segments text accordingly. To facilitate this, GraphRAG handles the one-time initialization and download of necessary NLTK (Natural Language Toolkit) resources, such as punkt and averaged_perceptron_tagger, through a bootstrapping mechanism (defined in graphrag/index/operations/chunk_text/bootstrap.py). This ensures that the required linguistic models are available without redundant operations. Each identified sentence then forms a TextChunk, retaining its source_doc_indices for context.

The overarching chunk_text function in graphrag/index/operations/chunk_text/chunk_text.py orchestrates these strategies. It takes a Pandas DataFrame as input, identifies the text column to be chunked, and dynamically loads the appropriate chunking strategy based on configuration (e.g., ChunkStrategyType.tokens or ChunkStrategyType.sentence). The system handles diverse input formats and supports progress tracking for long-running operations. The generated TextChunk objects, defined in graphrag/index/operations/chunk_text/typing.py, encapsulate the text content, source document indices, and token count, providing a standardized structure for downstream components.

Noun Graph Building and Extraction
Noun graphs are constructed by transforming unstructured text into a structured representation where noun phrases become nodes and their co-occurrence forms edges. This process begins with text unit processing, followed by the extraction of noun phrases, and finally, the establishment of relationships between them.

The core function for building the noun graph, located in graphrag/index/operations/build_noun_graph/build_noun_graph.py, orchestrates the extraction of nodes and edges. It takes a DataFrame of text units and a noun phrase extractor to identify noun phrases within the text. Node extraction involves identifying noun phrases, calculating their frequency, and linking them to the text units from which they originated. This module supports parallel processing and caching to optimize performance by avoiding redundant processing of identical text.

Edges are established based on the co-occurrence of noun phrases within the same text unit. All unique combinations of noun phrases found in a text unit are considered potential edges. These edges are then consolidated, with their weights initially based on the count of their co-occurrence. Optionally, these edge weights can be normalized using Pointwise Mutual Information (PMI) to refine the strength of the relationship between co-occurring noun phrases.

The system supports various methods for extracting noun phrases. The np_extractors directory within graphrag/index/operations/build_noun_graph/np_extractors provides a framework for different extraction techniques. These include:

Syntactic parsing-based extraction: Utilizes SpaCy's dependency parsing and named entity recognition for more accurate results. This method is implemented in SyntacticNounPhraseExtractor within graphrag/index/operations/build_noun_graph/np_extractors/syntactic_parsing_extractor.py, leveraging SpaCy's noun_chunks and doc.ents to identify and filter noun phrases based on various heuristics like token length and POS tags.
Context-Free Grammar (CFG) based extraction: Employs a CFG approach for noun chunk detection combined with optional named entity recognition, as detailed in CFGNounPhraseExtractor in graphrag/index/operations/build_noun_graph/np_extractors/cfg_extractor.py. This method iteratively applies grammar rules to merge adjacent tokens.
Regex-based extraction: Offers a faster, though potentially less accurate, alternative using regular expressions and TextBlob (with plans for future migration to SpaCy). This is implemented in RegexENNounPhraseExtractor within graphrag/index/operations/build_noun_graph/np_extractors/regex_extractor.py.
A factory, NounPhraseExtractorFactory in graphrag/index/operations/build_noun_graph/np_extractors/factory.py, manages the instantiation of these different extractors based on configuration. This allows for flexible selection of the most appropriate noun phrase extraction method for a given dataset or requirement. Helper utilities, such as those in graphrag/index/operations/build_noun_graph/np_extractors/np_validator.py, are used to validate and filter extracted noun phrases based on criteria like compound structure or token length, ensuring the quality of the resulting graph. Resource loaders in graphrag/index/operations/build_noun_graph/np_extractors/resource_loader.py manage the download and availability of necessary NLTK resources for these extraction processes.

Entity and Relationship Extraction
The process of transforming unstructured text into a structured knowledge graph involves sophisticated extraction of entities, relationships, and claims (covariates). GraphRAG leverages large language models (LLMs) to perform these extractions and then consolidates the results into DataFrames for subsequent knowledge graph construction.

The extraction of graph entities and relationships is managed by the graphrag/index/operations/extract_graph directory. This module orchestrates the process by taking text units as input and applying a specified extraction strategy. The default approach, ExtractEntityStrategyType.graph_intelligence, uses a GraphExtractor to interact with a ChatModel. This GraphExtractor prompts the LLM to identify entities (nodes) and relationships (edges) within the text. The LLM's structured output, which uses delimiters to separate records and fields, is then parsed and converted into a networkx graph. During this conversion, properties like descriptions and source IDs are aggregated, and edge weights are summed to ensure a comprehensive representation. The extracted entities and relationships are ultimately merged and formatted into pd.DataFrame objects, providing a standardized output for further processing. The system employs asynchronous and parallel processing to handle large datasets efficiently. For more details on the LLM integrations, refer to Language Model Integration and Prompt Tuning.

In addition to entities and relationships, GraphRAG also extracts structured claims, referred to as "covariates." This process is managed within the graphrag/index/operations/extract_covariates directory. Similar to entity extraction, this relies on LLMs, specifically using a ClaimExtractor to identify claims from text. The ClaimExtractor uses a ChatModel and predefined prompts to extract claims, which are structured as dictionaries containing fields such as subject_id, object_id, type, and description. To enhance extraction completeness, the system can perform iterative "gleaning," where the LLM is prompted multiple times to identify additional claims. The extracted claims are then cleaned, resolved against known entities, and transformed into Covariate dataclass instances, which are ultimately compiled into new rows in a pd.DataFrame. The system's design supports flexible configuration of LLM types, prompts, and extraction parameters, allowing adaptation to various data types and extraction goals.

Graph Enrichment and Analysis
Processes involved in enriching the constructed graph begin with generating numerical vector representations of both text content and graph nodes. Text embeddings are created using various strategies, supporting in-memory storage or persistence to a vector store. This functionality, orchestrated by embed_text in [/microsoft/graphrag/graphrag/index/operations/embed_text/embed_text.py], dynamically loads different embedding strategies, such as those for OpenAI models or mock implementations. For graph nodes, embeddings are generated using the Node2Vec algorithm, as handled by embed_graph in [/microsoft/graphrag/graphrag/index/operations/embed_graph/embed_graph.py]. This process transforms the graph's structural information into numerical vectors, which can optionally focus on the largest connected component of the graph.

Graph analysis continues with applying clustering algorithms to identify communities within the graph. The cluster_graph function in [/microsoft/graphrag/graphrag/index/operations/cluster_graph.py] utilizes hierarchical clustering, specifically the Leiden algorithm, to group related nodes into communities. This function can optionally operate on the stable largest connected component of the graph and allows for setting a maximum cluster size.

Graph metrics are also calculated, such as node degrees, which represent the number of connections each node has. The compute_degree function in [/microsoft/graphrag/graphrag/index/operations/compute_degree.py] generates a Pandas DataFrame containing the degree for each node. Additionally, the compute_edge_combined_degree function in [/microsoft/graphrag/graphrag/index/operations/compute_edge_combined_degree.py] calculates a "combined degree" for each edge by summing the degrees of its source and target nodes, providing a measure of edge importance within the graph's structure.

The system supports pruning the graph based on configurable criteria, such as node frequency, node degree, and edge weight. This process, implemented by prune_graph in [/microsoft/graphrag/graphrag/index/operations/prune_graph.py], helps in simplifying the graph and focusing on more relevant connections or components, including the option to retain only the stable largest connected component.

Finally, layout algorithms are applied to transform the structural information of the graph into spatial coordinates, which is essential for visualization. The layout_graph function in [/microsoft/graphrag/graphrag/index/operations/layout_graph/layout_graph.py] orchestrates this process, supporting UMAP-based layouts for generating 2D or 3D coordinates, and providing a zero-position fallback layout. These coordinates allow for visual representation of the graph, aiding in understanding its structure and relationships.

Text and Graph Embedding
The generation of numerical vector representations for both text content and graph nodes is a core capability within GraphRAG. These embeddings capture semantic and structural information, which is then used to enhance LLM outputs.

Text embedding, facilitated by the embed_text function in graphrag/index/operations/embed_text/embed_text.py, converts raw text into dense vector representations. This process supports various strategies, including using external LLMs like OpenAI, and can operate in two primary modes: returning embeddings directly for in-memory use or persisting them in a vector store for efficient retrieval. The system handles text preparation, intelligent batching to optimize API calls, and the recombination of embeddings when texts are split into smaller snippets. For example, the run function within graphrag/index/operations/embed_text/strategies/openai.py orchestrates these steps for OpenAI models, including splitting texts into manageable chunks, processing them in parallel, and reassembling their embeddings.

For graph structures, node embeddings are generated using the Node2Vec algorithm, primarily through the embed_graph function in graphrag/index/operations/embed_graph/embed_graph.py. This process transforms the structural context of nodes within a graph into numerical vectors. It can optionally preprocess the graph by focusing on its largest connected component to enhance embedding quality, particularly for noisy or disconnected graphs. The embed_node2vec function in graphrag/index/operations/embed_graph/embed_node2vec.py leverages external libraries to simulate random walks on the graph and learn representations, with configurable parameters controlling the embedding dimensions and walk characteristics.

Graph Clustering and Layout
GraphRAG identifies communities within a graph and transforms structural information into spatial coordinates for visualization. The system uses hierarchical clustering and graph layout algorithms to achieve these goals.

The clustering process identifies communities within a graph using the Leiden algorithm. This algorithm can operate on the entire graph or selectively on its largest connected component to simplify the process and reduce noise from isolated nodes. The result is a list of communities, each defined by its nodes and hierarchical level. For further details on how the extracted graph is processed, refer to Graph Enrichment and Analysis.

Graph layout algorithms translate the abstract connections of a graph into a visual representation by assigning spatial coordinates to each node. GraphRAG supports a UMAP-based layout, which projects high-dimensional node embeddings into a 2D or 3D space, reflecting the structural context of nodes. This process uses the UMAP algorithm to visualize graph structures effectively. A basic "zero-position" layout is also available as a fallback, placing all nodes at the origin. These layout coordinates are crucial for visualizing the complex relationships and communities within the knowledge graph, as demonstrated in the Unified Search Application.

Graph Component Summarization
GraphRAG generates concise summaries for various components of the knowledge graph, including individual entities, relationships, and higher-level community reports. This process leverages large language models (LLMs) to transform raw data and extracted information into more digestible and structured textual representations, crucial for enhancing the interpretability and utility of the graph.

For entity and relationship summarization, GraphRAG employs a flexible architecture that dynamically selects summarization strategies. The primary strategy, often referred to as "graph intelligence," involves using an LLM to condense multiple descriptive texts associated with an entity or relationship into a single, cohesive summary. This is managed by the summarize_descriptions function in /microsoft/graphrag/graphrag/index/operations/summarize_descriptions/summarize_descriptions.py, which orchestrates the process, handles concurrency for efficient processing of numerous graph components, and uses a PipelineCache to store LLM responses, avoiding redundant computations. The SummarizeExtractor class in /microsoft/graphrag/graphrag/index/operations/summarize_descriptions/description_summary_extractor.py is central to this, intelligently managing token limits by batching descriptions and iteratively summarizing them if necessary. Community summarization focuses on generating structured reports for identified communities within the graph. The summarize_communities function in /microsoft/graphrag/graphrag/index/operations/summarize_communities/summarize_communities.py is responsible for orchestrating the creation of CommunityReport objects. These reports include a title, summary, key findings, and a rating, providing a comprehensive overview of each community. The system supports hierarchical community structures, meaning it can generate reports for communities at different levels of granularity. This "mixed context" approach, handled by functions like build_mixed_context in /microsoft/graphrag/graphrag/index/operations/summarize_communities/build_mixed_context.py and within the graph_context directory, ensures that the LLM receives the most pertinent information without exceeding its token capacity. The CommunityReportsExtractor in /microsoft/graphrag/graphrag/index/operations/summarize_communities/community_reports_extractor.py, leveraging Pydantic models, is used to ensure the LLM's output conforms to a predefined structured schema, facilitating programmatic consumption of the generated reports.

Incremental Indexing Capabilities
GraphRAG provides mechanisms for updating existing knowledge graphs with new information without rebuilding them entirely. This process ensures that changes in input data are identified and seamlessly integrated into the current entities, communities, and relationships.

The system begins by identifying changes in the input data. It compares the incoming dataset with previously stored documents to pinpoint both new and deleted entries. This delta identification is crucial for determining which parts of the knowledge graph require modification. Once changes are identified, the system concatenates existing and new dataframes for various graph components.

For entities, GraphRAG merges existing and new entities. When entities with the same title are encountered, it resolves conflicts by grouping them and aggregating attributes such as description and text_unit_ids. Descriptions are collected into a list, and associated text_unit_ids are flattened to ensure all relevant text units are linked. New entities are assigned unique human_readable_id values to maintain consistency and prevent ID clashes.

Similarly, for communities and their reports, the system integrates new community data by assigning fresh, unique IDs to avoid conflicts with existing communities. This ID mapping is then propagated to related community reports, ensuring that all components consistently reference the updated community structure.

Relationship data also undergoes a merging and conflict-resolution process. When relationships share the same source and target, their properties, such as description, text_unit_ids, weight, and combined_degree, are aggregated or recalculated. New relationships receive unique human_readable_id values, and derived properties like source_degree, target_degree, and combined_degree are re-evaluated to reflect the updated graph structure.

Throughout these update processes, GraphRAG maintains data consistency by standardizing column schemas and ensuring unique ID assignments across all entities, communities, and relationships. This approach allows for efficient updates to the knowledge graph, minimizing the computational overhead associated with full re-indexing while preserving the integrity of the stored information.

GraphRAG integrates various large language models (LLMs) to enhance its capabilities, providing a standardized framework for interacting with different LLM providers, managing model caching, and ensuring consistent functionality for tasks such as embedding generation and conversational interactions. This integration allows GraphRAG to leverage the power of LLMs across its data pipeline and query functionalities.

A ModelManager class, implemented as a singleton in graphrag/language_model/manager.py, centrally registers and manages instances of chat and embedding LLMs. This manager ensures that models are consistently created and retrieved, preventing redundant resource allocation and offering a unified interface for model access. The actual creation of these models is handled by a ModelFactory in graphrag/language_model/factory.py, which supports the registration of new LLM implementations and instantiates them based on specified model types.

To maintain consistency and interoperability across different LLM implementations, GraphRAG defines a set of standard protocols in graphrag/language_model/protocol. These protocols, including EmbeddingModel for generating numerical vector representations of text and ChatModel for conversational interactions, specify the required methods and configurations for LLMs, supporting both asynchronous and synchronous operations as well as streaming capabilities. This standardization facilitates type-checking and simplifies the integration of new model providers.

GraphRAG includes concrete implementations for popular LLM providers. The FNLLM Provider in graphrag/language_model/providers/fnllm integrates OpenAI and Azure OpenAI models, offering features like caching and error handling. For broader LLM support, the LiteLLM Provider in graphrag/language_model/providers/litellm provides robust request management functionalities, including rate limiting, retries, and comprehensive logging. A key aspect of LLM integration is caching. GraphRAG employs an asynchronous key-value caching infrastructure, defined by the ModelCache protocol in graphrag/language_model/cache. This mechanism optimizes performance by storing and retrieving model responses, reducing the need for repetitive LLM calls. Additionally, a standardized event handling system, specified by the ModelEventHandler protocol in graphrag/language_model/events, processes and responds to errors that occur during language model operations, ensuring flexible error management.

Beyond basic LLM interaction, GraphRAG extensively utilizes prompt tuning to optimize the performance and output quality of its knowledge graph generation and query processes. Prompt tuning involves carefully crafting inputs to LLMs to guide their responses for specific tasks. The prompt tuning framework within GraphRAG enables both default and dynamic generation of prompts for various tasks, including creating personas, identifying entity types, extracting relationships, and summarizing community reports.

The process often begins with document loading and sampling, managed by modules in graphrag/prompt_tune/loader. This involves chunking raw text into manageable units and then intelligently sampling these chunks. Different sampling strategies are supported, such as selecting top chunks, random sampling, or an embedding-based selection method that identifies chunks most relevant to a central theme.

Once documents are prepared, dynamic prompt generation takes over. Modules in graphrag/prompt_tune/generator are responsible for creating a wide array of prompts. This includes generating detailed LLM personas, which define the AI's role and tone for specific tasks, and identifying relevant entity types from input documents. Prompts for extracting entities and relationships are also dynamically generated, often leveraging few-shot examples to guide the LLM on expected output formats (e.g., JSON or tuple-delimited structures). Furthermore, the system generates prompts for summarizing different graph components, such as community reports and entity descriptions, ensuring that LLMs produce concise and relevant summaries.

The raw and structured prompt templates used for these generation tasks are stored in graphrag/prompt_tune/prompt and graphrag/prompt_tune/template, respectively. These templates define the expected output formats and content for various tasks, including persona generation, entity extraction, relationship identification, domain detection, and summarization. The use of placeholders within these templates allows for dynamic insertion of context and parameters, making the prompt generation process flexible and adaptable to different scenarios. GraphRAG's prompts are also stored in a separate graphrag/prompts directory, ensuring structured information extraction, graph generation, community report generation, and multi-faceted query response processing. These prompts guide LLMs in both indexing and query operations, ensuring structured, attributable, and contextually relevant responses.

Standardized Language Model Protocols
The graphrag system defines foundational protocols for Language Model (LM) interfaces, ensuring consistency and interoperability across various implementations. These protocols, primarily defined in /microsoft/graphrag/graphrag/language_model/protocol/base.py, leverage Python's Protocol to specify required methods for both embedding generation and conversational interactions. This design choice allows for decoupling, where implementations can conform to these interfaces without direct inheritance, and facilitates type-checking during static analysis.

Two primary protocols govern LM interactions:

EmbeddingModel: This protocol establishes the interface for LMs designed to generate numerical vector embeddings from text. It mandates methods such as aembed_batch, aembed, embed_batch, and embed, supporting both asynchronous and synchronous operations for single or batched text inputs. Implementations are expected to provide the logic for these methods, typically by calling an underlying embedding model API.
ChatModel: This protocol defines the interface for LMs used in conversational contexts. It requires methods like achat, achat_stream, chat, and chat_stream for generating chat responses, including streaming capabilities for real-time feedback. These methods support both asynchronous and synchronous operations and accommodate conversation history for context management.
Both protocols include a config attribute, allowing for the pass-through of model-specific configuration settings. This standardized approach ensures that different LM providers can be integrated and swapped seamlessly while maintaining consistent functionality across the graphrag system. Details on specific provider implementations can be found in Language Model Providers and Their Implementations.

Structured Search Algorithms and RAG Techniques
GraphRAG implements various Retrieval-Augmented Generation (RAG) techniques to perform structured searches, leveraging Large Language Models (LLMs) for diverse querying needs. These techniques are built upon an abstract BaseSearch interface, which defines a consistent contract for all search implementations, including methods for both complete and streaming search results. The system tracks detailed metrics such as LLM calls, prompt tokens, and output tokens for each search operation, providing observability into performance and resource usage.

Basic Search
The BasicSearch algorithm provides a generic RAG approach for straightforward structured queries. It constructs context by semantically searching raw text chunks, ensuring the selected information adheres to token limits, and then uses an LLM to generate answers. This method supports streaming capabilities, allowing for incremental response generation. For more details on the context building mechanisms, see Context Building Mechanisms.

DRIFT Search
The "Drift Reduction in Fact-checking" (DRIFT) search mechanism provides an iterative, multi-step process for complex queries. It begins with a primer stage that decomposes the initial query and generates hypothetical answers and subqueries using community reports. The search process then proceeds through a series of actions, managed as a graph of DriftAction objects, where each action represents a step in the iterative search. This involves orchestrating parallel local searches, which synthesize information from various sources to reduce results into a comprehensive answer. The system meticulously tracks LLM token usage throughout this process.

Global Search
The GlobalSearch strategy employs a map-reduce approach to process information from diverse structured data sources. It performs parallel LLM calls on chunks of context data, aggregates the intermediate answers, and then synthesizes a final, coherent response using another LLM call. This strategy is designed to handle broader, community-level queries and supports dynamic community selection to adaptively narrow down the search space.

Local Search
The LocalSearch algorithm focuses on building comprehensive contextual data from various sources, including entities, community reports, text units, relationships, and covariates. It employs token-aware truncation and ranking to prioritize and fit the most relevant information within LLM token limits, formulating prompts to generate responses for highly localized queries. This approach ensures that the LLM's answers are grounded in specific, contextualized data.

Basic Search: Raw Text Chunk RAG
The BasicSearch algorithm within GraphRAG implements a Retrieval Augmented Generation (RAG) approach for straightforward queries. It leverages semantic search to identify relevant raw text chunks, which are then used to construct a contextual prompt for a large language model (LLM).

The process begins with building a search context. This involves using semantic similarity to retrieve relevant TextUnit objects from a vector store. These retrieved text units are then pruned to fit within a specified token limit, ensuring that the context provided to the LLM remains manageable. The BasicSearchContext class, defined in /microsoft/graphrag/graphrag/query/structured_search/basic_search/basic_context.py, is responsible for this context construction, including formatting the selected text units into a delimited string for the prompt.

Once the context is built, the BasicSearch class, implemented in /microsoft/graphrag/graphrag/query/structured_search/basic_search/search.py, orchestrates the interaction with the LLM. It formulates a system prompt by incorporating the retrieved context and a defined response type. This prompt is then sent to a ChatModel to generate an answer. The system supports both direct response generation and streaming responses, where text chunks are yielded as they are produced by the LLM. During this process, QueryCallbacks are utilized to report events such as new LLM tokens and the generated context, and metrics such as LLM calls and token usage are tracked for performance analysis.

DRIFT Search: Iterative Fact-checking
The "Drift Reduction in Fact-checking" (DRIFT) search mechanism is an iterative, multi-step process designed to answer complex queries by progressively refining information. This approach breaks down a main query into smaller sub-queries, executes them, and synthesizes the results into a comprehensive answer, employing Large Language Models (LLMs) and structured graph-based state management.

At its core, the DRIFT mechanism manages individual search steps, or actions, through DriftAction objects, as defined in graphrag/query/structured_search/drift_search/action.py. Each DriftAction encapsulates a specific query, its potential answer, a relevance score, and any subsequent follow-up actions, forming a hierarchical search path. This structure is maintained within a graph of actions, orchestrated by the QueryState class in graphrag/query/structured_search/drift_search/state.py. The QueryState tracks the progression of a DRIFT query, allowing for the addition of actions, establishing relationships between them, identifying incomplete actions, and ranking them for subsequent processing. It also manages the serialization of this graph state for persistence and aggregates LLM token usage across all actions.

The process begins with query decomposition and expansion, handled by the DRIFTPrimer in graphrag/query/structured_search/drift_search/primer.py. This component leverages community reports to generate hypothetical answers and sub-queries, essentially expanding the initial query to create a richer context for subsequent embedding. The PrimerQueryProcessor further refines this by expanding a query into a hypothetical answer and then embedding it, a technique akin to Hypothetical Document Embedding (HyDE), which enriches the context for deeper semantic analysis.

Context building is a crucial precursor to the iterative search. The DRIFTSearchContextBuilder in graphrag/query/structured_search/drift_search/drift_context.py is responsible for preparing this context by identifying the most relevant community reports. It achieves this by converting reports into a standardized data format, computing the cosine similarity between the query embedding and the embeddings of community reports, and selecting the top-k reports based on their relevance. This ensures that the subsequent local searches are focused on the most pertinent information.

The orchestration of the entire DRIFT search is managed by the DRIFTSearch class in graphrag/query/structured_search/drift_search/search.py. This class extends Structured Search Algorithms and RAG Techniques and initiates the process by calling the DRIFTPrimer for the initial query breakdown. It then enters an iterative loop, where incomplete DriftAction objects are ranked, selected, and executed in parallel using local searches. These local searches are performed by a LocalSearch instance, which synthesizes contextual data from various sources like entities, community reports, and text units. Finally, after the iterative search, the collected responses from the QueryState are reduced into a single, coherent answer using the ChatModel, ensuring a comprehensive response to the original complex query. The DRIFTSearch also meticulously tracks LLM calls and token usage throughout its various stages, providing valuable metrics for performance and cost analysis.

Global Search: Map-Reduce Across Structured Data
The GlobalSearch strategy employs a map-reduce approach to process information from diverse data sources, synthesizing answers to queries by leveraging Large Language Models (LLMs). This multi-step process begins with constructing context relevant to the query. A GlobalContextBuilder, primarily implemented by the GlobalCommunityContext class in /microsoft/graphrag/graphrag/query/structured_search/global_search/community_context.py, dynamically selects relevant community reports to build this context. This dynamic selection may involve an LLM to filter or rank community_reports based on the input query, ensuring the most pertinent information is included.

Once the context is prepared, the search proceeds in two main phases:

Map Phase: This phase involves parallel LLM calls, where each individual chunk of context data is processed to generate initial answers or key points. These responses are expected to be structured as JSON objects containing a list of points, each with a description and a relevance score. Concurrency during these parallel calls is managed using an asyncio.Semaphore within the GlobalSearch class in /microsoft/graphrag/graphrag/query/structured_search/global_search/search.py.

Reduce Phase: The intermediate answers from the map phase are then aggregated and filtered based on their relevance scores. The relevant key points are sorted, and another LLM call synthesizes these into a final, coherent response to the original query. This phase can optionally incorporate general knowledge if the system is configured to allow it, serving as a fallback when provided data is insufficient.

The GlobalSearch class offers both streaming and batch search capabilities, allowing for real-time response generation or a complete, structured result. Throughout this process, QueryCallbacks are integrated, enabling external systems to monitor various stages of the search, such as the start and end of map responses, context building, and LLM token generation. The system also supports custom system prompts for both the map and reduce phases, offering flexibility in prompt engineering. More details on structured search algorithms can be found in Structured Search Algorithms and RAG Techniques.

Local Search: Contextual Data Synthesis
The LocalSearch algorithm orchestrates the process of generating responses to highly localized queries by synthesizing contextual data from diverse sources within the knowledge graph. This approach ensures that responses are grounded in specific facts and relationships relevant to the query.

The core of LocalSearch involves two main components: a context builder and a language model interaction layer. The LocalSearchMixedContext class within graphrag/query/structured_search/local_search/mixed_context.py is responsible for intelligently gathering and structuring contextual information. This builder integrates various data sources, including entities, community reports, text units, relationships, and covariates. It employs a token-aware truncation and ranking mechanism to prioritize and include the most relevant information within a specified token limit. This ensures that the language model receives a concise yet comprehensive context, preventing token overflow while maximizing relevance. The context building process considers factors such as entity mapping from the user query, conversation history, and the relevance of community reports, entities, relationships, and text units to the selected entities.

Once the context is built, the LocalSearch class in graphrag/query/structured_search/local_search/search.py formulates a system prompt using this contextual data and interacts with a language model to generate a response. This interaction can either collect the full response or stream it back in chunks, enabling real-time updates. The system also tracks various metrics, including completion time and token usage, to monitor performance and cost. The integration of QueryCallbacks allows for external systems to be notified of new tokens and the context used during the query process. For further details on the overarching structured search algorithms and RAG techniques, see Structured Search Algorithms and RAG Techniques.

Dynamic Community Selection
The DynamicCommunitySelection process iteratively selects relevant CommunityReport instances from a collection based on a query. This mechanism is crucial for efficiently identifying the most pertinent information within a large knowledge graph to answer a user's question, especially within the context of retrieval-augmented generation (RAG) techniques.

The selection begins with a set of root communities and employs a modified breadth-first search. In each iteration, the system uses a language model to rate the relevance of communities to the input query. This relevance scoring is performed by the rate_relevancy function, which prompts a ChatModel to evaluate how well a community's description aligns with the query. The output includes a numerical rating and the reasons for that rating, structured as a JSON object. This process can be repeated multiple times for a single community, with the most frequent rating determining the consensus score, which helps to mitigate variance in LLM responses. See Language Model Integration and Prompt Tuning: Language Model Providers and Their Implementations for more details on the ChatModel.

Communities that meet a predefined relevance threshold are considered relevant. For these relevant communities, their children in the community hierarchy are added to a queue for subsequent rating. This relevance pruning helps to narrow the search space, focusing on promising branches of the community graph. To manage the computational load and adhere to API rate limits, the system utilizes asyncio.Semaphore to control the number of concurrent language model calls during the rating process. If a particular level in the hierarchy yields no relevant communities, the system can expand its search to all communities at the next level, up to a specified maximum depth, preventing premature termination in cases where relevant information might reside deeper in the graph structure. The DynamicCommunitySelection class within graphrag/query/context_builder/dynamic_community_selection.py orchestrates this entire process, ultimately returning a refined list of relevant CommunityReport objects.

Entity Extraction and Ranking
Entity extraction and ranking within GraphRAG involves identifying and prioritizing Entity objects based on their relevance to a query or their connections within the knowledge graph. This process is crucial for contextualizing information and retrieving pertinent data.

One mechanism for extracting entities is map_query_to_entities, which leverages vector stores to find semantically similar entities. This function processes a natural language query by embedding it and then performing a similarity search against a text_embedding_vectorstore. The results are then matched to Entity objects, potentially including or excluding specific entities based on configuration. If no query is provided, this function defaults to retrieving the highest-ranked entities.

A complementary mechanism is find_nearest_neighbors_by_entity_rank, which focuses on identifying entities directly related to a specified entity through Relationship objects. This function navigates the graph structure to find connected entities and then ranks them based on their rank attribute, allowing for the retrieval of the most significant related entities. This approach is useful for exploring the local neighborhood around a particular entity in the knowledge graph. The valid keys for identifying entities in vector stores, such as ID or TITLE, are defined by EntityVectorStoreKey in graphrag/query/context_builder/entity_extraction.py. The overall context-building process for various search modes relies on these extraction capabilities to gather relevant information for language model prompts. For details on how context is built around these entities, refer to Context Building Mechanisms.

Conversation History Management
The management of conversational data within GraphRAG is facilitated by dedicated data structures and a ConversationHistory class, primarily designed to structure interactions for language model prompts. This system uses an enumeration, ConversationRole, to classify turns as either SYSTEM, USER, or ASSISTANT, ensuring clear identification of who is speaking. Individual conversational exchanges are captured by the ConversationTurn dataclass, which pairs a role with its textual content. For more structured analysis, these turns can be grouped into QATurn objects, representing a question-answer pair. A QATurn consists of a user query and a list of assistant responses, offering a consolidated view of each interaction.

The ConversationHistory class serves as the central component for aggregating and manipulating these conversational elements. It allows for the addition of new ConversationTurn objects and can transform a linear history into a series of QATurn objects. A key method within ConversationHistory is build_context, which prepares the conversation history into a formatted string and a pd.DataFrame suitable for use as system prompt context. This method is particularly important for interactions with token-limited language models, as it can restrict the context size using a tokenizer. It supports options such as prioritizing recent interactions through recency_bias, selectively including only user questions via include_user_turns_only, and limiting the number of question-answer turns. This ensures that the conversation context provided to language models is both relevant and adheres to specified token constraints.

Query Input and Data Adaptation
GraphRAG's query engine relies on robust data adaptation strategies to bridge the gap between the raw outputs of the indexing engine and the structured data models used for querying. This involves transforming data from its initial pd.DataFrame format into GraphRAG's internal data_model objects and then facilitating the retrieval, filtering, and conversion back to pd.DataFrames for efficient processing and display.

The process of loading raw indexing engine outputs into GraphRAG's data model objects is handled by the input loaders, primarily found in the graphrag/query/input/loaders directory. Specifically, the functions within graphrag/query/input/loaders/dfs.py are responsible for converting pd.DataFrames into lists of Entity, Relationship, Community, CommunityReport, TextUnit, and Covariate objects. These functions meticulously map DataFrame columns to the attributes of the respective data model objects, ensuring that data is correctly parsed and standardized. Helper utilities in graphrag/query/input/loaders/utils.py provide robust type conversion and safe data retrieval, gracefully handling missing or unexpected data types during this transformation.

Once the data is in GraphRAG's structured data model format, the query engine provides mechanisms for retrieving and filtering these objects. The retrieval components, located in graphrag/query/input/retrieval, enable focused access to specific entities, relationships, text units, community reports, and covariates based on various criteria. For instance, get_entity_by_id in graphrag/query/input/retrieval/entities.py allows fetching entities by their unique identifiers, while get_in_network_relationships in graphrag/query/input/retrieval/relationships.py can filter relationships connected to a specified set of entities. After retrieval and filtering, these structured data model objects can be converted back into pd.DataFrames using functions like to_entity_dataframe or to_relationship_dataframe. This re-conversion provides a standardized tabular format for downstream query processing and easier integration with analytical tools. The adaptation module graphrag/query/indexer_adapters.py further refines this process by transforming raw indexer DataFrames into the data model objects, handling additional aspects like community level roll-ups and content embedding if necessary, thereby preparing a comprehensive set of data for the query system.

Input Data Loaders
The input loaders within GraphRAG are responsible for transforming tabular data, typically stored in Pandas DataFrames, into structured data model objects. This process is essential for preparing raw data for GraphRAG's knowledge graph construction and querying mechanisms. The graphrag/query/input/loaders/dfs.py module provides functions designed to convert DataFrames into lists of entities, relationships, communities, text units, covariates, and community reports.

Each function within graphrag/query/input/loaders/dfs.py maps DataFrame columns to the attributes of specific data model objects, such as id, title, type, source, target, and description. For instance, read_entities creates Entity objects, while read_relationships constructs Relationship objects. This mapping can be customized to accommodate various input data schemas. To ensure data consistency and prevent errors, these loading functions rely on a set of utility functions located in graphrag/query/input/loaders/utils.py. These utilities handle safe retrieval of values from dictionary-like objects and perform type conversions (e.g., to string, list, integer, float, or dictionary), along with validation. They also distinguish between required and optional fields, gracefully handling missing data by returning None for optional fields without raising exceptions, thereby enhancing the robustness of the data loading process. The design allows for flexible inclusion of arbitrary additional DataFrame columns into an attributes dictionary on the data model object, supporting extensible data representations. For a deeper understanding of the data models utilized by these loaders, refer to Core Data Models and Schemas.

Data Retrieval and Filtering
GraphRAG's query engine includes mechanisms for retrieving and filtering various structured data model objects, which are transformed from raw indexing engine outputs into a format suitable for efficient query processing. These mechanisms focus on extracting entities, relationships, text units, community reports, and covariates based on specific criteria, and then converting them into pandas DataFrames.

For entities, utilities exist to retrieve Entity objects by their ID, name, or specific attributes. This includes robust handling for UUIDs, accommodating both dashed and undashed formats for identification. Once retrieved, these entities can be converted into a pd.DataFrame that includes standard fields along with dynamic columns derived from their attributes, enabling a flexible tabular representation.

Relationship retrieval involves filtering Relationship objects based on their connection to a set of selected entities. This includes identifying relationships where both source and target entities are within the selected group (get_in_network_relationships), relationships connecting selected entities to external ones (get_out_network_relationships), or any relationship involving selected entities (get_candidate_relationships). The retrieved relationships can then be sorted by a specified ranking attribute and converted into a pd.DataFrame, similar to entities, with dynamic columns for their attributes.

Text unit retrieval focuses on identifying TextUnit objects linked to particular entities. This involves collecting the text unit IDs associated with selected entities and filtering the available text units to match those IDs. The selected text units are then transformed into a pd.DataFrame that includes their short ID, text content, and any associated attributes.

Community reports can be retrieved by identifying CommunityReport instances associated with selected entities based on their community IDs. These reports are then converted into a pd.DataFrame, which can include either a summary or the full content of the report, along with an optional rank and dynamic attribute columns.

Finally, covariates are filtered to select those whose subject ID matches the title of any of the selected entities. These filtered Covariate objects are then transformed into a pd.DataFrame containing their ID, associated entity, and dynamic columns derived from their attributes.

The consistent use of pd.DataFrames across these retrieval functions provides a standardized and efficient way to handle structured data, supporting further analysis and display within the GraphRAG system. These data adaptation strategies ensure that the query engine can effectively utilize the structured knowledge graphs generated by the Indexing Engine.

Question Generation
GraphRAG includes a modular framework for generating follow-up questions from chat history and contextual information. This capability enhances user interaction by providing relevant subsequent queries.

The foundation for this system is defined by the BaseQuestionGen abstract base class located in /microsoft/graphrag/graphrag/query/question_gen/base.py. This class establishes a common interface for all question generation implementations, ensuring consistency in how questions are generated. It mandates both synchronous (generate) and asynchronous (agenerate) methods, which take question_history, optional context_data, and a desired question_count as input. The output of these operations is encapsulated in the QuestionResult dataclass, also defined in /microsoft/graphrag/graphrag/query/question_gen/base.py. This structured result includes the generated questions, the context data utilized, completion time, the number of LLM calls made, and the tokens consumed, providing comprehensive details about each generation attempt.

A concrete implementation of this framework is the LocalQuestionGen class, found in /microsoft/graphrag/graphrag/query/question_gen/local_gen.py. This class leverages a language model (ChatModel) and a LocalContextBuilder to create new questions. When called, LocalQuestionGen processes the existing question_history and, if necessary, dynamically builds additional context_data using the LocalContextBuilder. It then formats a system prompt that incorporates this context and the desired number of questions. The generated prompt is sent to the ChatModel to produce the follow-up questions. The process supports streaming responses from the language model and integrates callback mechanisms for extensibility. This integration of conversation history and dynamic context allows the system to generate questions that are pertinent to the ongoing dialogue and the underlying knowledge graph. For further details on conversation history management, refer to Conversation History Management.

API Indexing Functions
The primary entry point for orchestrating GraphRAG's indexing pipeline is the build_index function, located in /microsoft/graphrag/graphrag/api/index.py. This asynchronous function manages the entire process of converting unstructured text into a structured knowledge graph, supporting both initial indexing runs and updates to existing graphs.

The build_index function is responsible for initializing loggers and setting up WorkflowCallbacks to manage lifecycle events throughout the pipeline's execution. For update scenarios, a helper function standardizes the indexing method string by appending "-update", distinguishing these runs from initial builds and ensuring incremental changes are handled correctly.

The overall architecture, which build_index is a part of, is designed to be non-blocking and enables integration into event-driven applications, allowing for efficient processing of large datasets. The abstraction of the pipeline creation and execution within build_index ensures a clear separation of concerns, making the system modular and easier to maintain. Unified Search Application
The unified search application provides a Dockerized Streamlit interface for exploring and comparing GraphRAG search results across various datasets. This application is designed to visualize graph data, generate suggested questions, and manage data configurations and application state, offering an interactive environment for evaluating the GraphRAG system.

The application's deployment is managed via a Dockerfile, which sets up the necessary Python environment and dependencies for execution. The core application logic, found in /microsoft/graphrag/unified-search-app/app/app_logic.py, orchestrates session variables, loads datasets and knowledge models, and dispatches user queries to different search functionalities. This includes concurrent execution of various Retrieval-Augmented Generation (RAG) search types, such as basic, global, DRIFT, and local search, as well as the generation of suggested questions. The application integrates with GraphRAG's querying capabilities, as described in the Query Engine section.

For knowledge loading and data abstraction, the application utilizes a dedicated component within the /microsoft/graphrag/unified-search-app/app/knowledge_loader directory. This component abstracts data access, retrieving graph-indexed data from either local files or Azure Blob Storage and structuring it into a KnowledgeModel for GraphRAG functions. Data configurations, such as table names for graph-indexed data and default settings for LLM interactions, are centralized in /microsoft/graphrag/unified-search-app/app/data_config.py. Caching mechanisms are employed to optimize performance during data retrieval.

Application state management is handled by the components in /microsoft/graphrag/unified-search-app/app/state. This includes SessionVariable for abstracting Streamlit's st.session_state and QueryVariable for synchronizing variables with URL query parameters, ensuring state persistence and shareability. The user interface, defined in /microsoft/graphrag/unified-search-app/app/ui, includes components like a sidebar for configuration, a search result display with hyperlinked citations, an interactive graph visualization, and listings of community reports and suggested questions. The main entry point for the Streamlit application is in /microsoft/graphrag/unified-search-app/app/home_page.py, which orchestrates UI rendering, user input, and the display of search results and the graph explorer.

Core Application Logic and Flow
The Streamlit application's core logic, primarily encapsulated within the unified-search-app/app/app_logic.py file, orchestrates the user experience from data loading to displaying search results. It manages the application's state through SessionVariables, ensuring continuity across user interactions.

Upon initialization, the system configures the Streamlit page and loads a listing of available datasets. Users can then select a dataset, which triggers the loading of its corresponding knowledge model, comprising entities, relationships, communities, and other graph-indexed data. This loading process is optimized using caching mechanisms.

For query processing, the application dispatches user questions to various Retrieval Augmented Generation (RAG) search functionalities, including Basic, Global, DRIFT, and Local searches. These searches can be run concurrently, improving responsiveness. The system also supports generating suggested questions based on the active dataset. The results from these searches, along with generated questions, are then presented to the user through a dynamic interface, which includes detailed search outcomes, citations, and interactive graph visualizations. For more details on the application's user interface, refer to User Interface Components and Interaction. Knowledge Loading and Data Abstraction
The knowledge_loader component in GraphRAG is responsible for abstracting data access, retrieving graph-indexed data, and structuring it for use by various GraphRAG functions, while also leveraging caching for performance. This system allows the application to handle data originating from either local files or Azure Blob Storage, providing flexibility in deployment and data management.

The process begins with an abstraction layer for data sources. A Datasource abstract base class defines a common interface for reading and writing data, along with methods for reading configuration settings and checking for table existence. This enables interchangeable data source implementations. Concrete implementations include LocalDatasource for local file system access and BlobDatasource for Azure Blob Storage. A dynamic selection mechanism, implemented in unified-search-app/app/knowledge_loader/data_sources/loader.py, determines which data source to use based on environment variables. This allows the application to seamlessly switch between development and production environments without code changes. These data sources are responsible for loading structured data, such as Parquet files for tabular data and YAML files for configurations, including dataset listings and prompt configurations.

Once a data source is established, the knowledge_loader focuses on preparing the graph-indexed data. Functions within unified-search-app/app/knowledge_loader/data_prep.py retrieve various data types including entities, relationships, covariates, text units, and community reports, converting them into pd.DataFrame objects. To enhance performance, these data loading operations are cached using Streamlit's caching mechanism, with a configurable time-to-live. This prevents redundant data retrieval, especially in an interactive application setting.

Finally, the loaded data is consolidated into a unified KnowledgeModel. The unified-search-app/app/knowledge_loader/model.py module orchestrates the individual data loading calls and aggregates the resulting dataframes into this dataclass object. This KnowledgeModel provides a cohesive structure, encapsulating all graph-indexed information for subsequent use by GraphRAG's querying and other functionalities. The construction of this model also benefits from caching for its individual components, ensuring efficient access to the complete knowledge graph.

Data Source Implementations
GraphRAG's unified search application utilizes data source implementations to retrieve knowledge from various storage backends. The primary goal is to abstract the underlying storage mechanism, allowing the application to seamlessly load data and configurations. This is achieved through specific concrete implementations: LocalDatasource for local file systems and BlobDatasource for Azure Blob Storage.

The LocalDatasource implementation, defined in unified-search-app/app/knowledge_loader/data_sources/local_source.py, focuses on reading data from the local file system. It can read Parquet files into pd.DataFrame objects and load GraphRagConfig settings from local YAML files. It also handles the loading of prompt configurations from specified local directories.

Conversely, the BlobDatasource implementation, found in unified-search-app/app/knowledge_loader/data_sources/blob_source.py, connects to Azure Blob Storage to access data. It supports reading Parquet files and YAML configurations from blob containers, leveraging DefaultAzureCredential for authentication. Both LocalDatasource and BlobDatasource adhere to the Datasource abstract base class defined in unified-search-app/app/knowledge_loader/data_sources/typing.py, ensuring a consistent interface for data access regardless of the storage backend.

The selection between these data source implementations is handled dynamically by the create_datasource function, located in unified-search-app/app/knowledge_loader/data_sources/loader.py. This function checks for the presence of an BLOB_ACCOUNT_NAME environment variable. If configured, it instantiates and returns a BlobDatasource; otherwise, it defaults to a LocalDatasource. This approach allows for flexible deployment across different environments without requiring code modifications. This dynamic selection and abstraction ensure that the application can efficiently manage and retrieve indexed graph data and configurations from diverse storage locations.

Application State Management and Persistence
The unified search application manages its internal state and user interactions through a structured approach that abstracts Streamlit's native session management. This ensures data consistency across user sessions and enables the persistence of certain configurations via URL parameters, making application states shareable.

Core to this system are two classes: SessionVariable and QueryVariable. The SessionVariable class, defined in [unified-search-app/app/state/session_variable.py](/microsoft/graphrag/unified-search-app/app/state/session_variable.py), provides a wrapper around Streamlit's st.session_state. This abstraction allows developers to interact with session-persisted data using a property-based interface rather than direct dictionary access, simplifying code and preventing naming collisions through an inferred variable name and optional prefix. This class is responsible for ensuring default values are set for variables if they are not already present in the session state.

For state variables that need to be reflected in or initialized from the application's URL, the QueryVariable class, found in [unified-search-app/app/state/query_variable.py](/microsoft/graph/graphrag/unified-search-app/app/state/query_variable.py), is used. This class links a variable in st.session_state to a corresponding URL query parameter in st.query_params. It automatically handles the conversion of boolean values to and from lowercase string representations (e.g., "true" or "false") for URL compatibility. This synchronization allows users to share application states directly through URLs, providing a persistent and reproducible view of the application.

All application-wide session and query-persistent variables are centralized within the SessionVariables class, located in [unified-search-app/app/state/session_variables.py](/microsoft/graphrag/unified-search-app/app/state/session_variables.py). This class instantiates various SessionVariable and QueryVariable objects to manage aspects such as the selected dataset, user questions, search toggles (e.g., for global, local, drift, or basic RAG searches), and display settings for graph visualizations. By consolidating these variables, SessionVariables establishes a consistent default state for the application and ensures structured access and modification of dynamic configurations. This structured approach to state management is integral to the Unified Search Application's ability to maintain user context and facilitate interactive exploration of search results and knowledge graphs.

User Interface Components and Interaction
The Streamlit application provides a visual interface for interacting with GraphRAG's capabilities. A central component is the sidebar, managed by the functions in unified-search-app/app/ui/sidebar.py, which offers controls for dataset selection, the number of suggested questions, and toggles for various search modes like "Include basic RAG," "Include local search," "Include global search," and "Include drift search." User interactions with these elements are synchronized with the application's state, enabling dynamic configuration of queries.

Search results are displayed within the main interface, with the unified-search-app/app/ui/search.py module handling the presentation. This includes rendering the LLM-generated response, associated statistics, and detailed citations. A key feature is the dynamic creation of hyperlinks within the response text, allowing users to navigate directly to the corresponding citation details displayed in HTML tables. This module also manages the initial setup of search UI placeholders and the formatting of suggested questions.

The application includes an interactive graph visualization, facilitated by unified-search-app/app/ui/full_graph.py. This component displays entities and their community relationships, allowing users to explore the graph structure at different community levels. The visualization uses altair for plotting, presenting entities based on their coordinates, colored by community, and sized by their degree within the graph.

For knowledge exploration, the application presents community reports through a listing and detailed view. The unified-search-app/app/ui/report_list.py module manages a list of available community reports, allowing users to select a specific report. Once selected, unified-search-app/app/ui/report_details.py displays the report's full content, including its title, summary, findings, and a breakdown of associated entity and relationship citations. Additionally, unified-search-app/app/ui/questions_list.py displays a list of AI-generated follow-up questions, enabling users to easily select and explore related inquiries. These UI components leverage Streamlit's capabilities for interactive data display and session state management to provide a cohesive user experience.
